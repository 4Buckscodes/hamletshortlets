# HAMLET Mobile

Native Android and iOS application for HAMLET, built with Expo SDK 58, React Native 0.88, TypeScript and Expo Router.

## Product direction

One app with role-aware experiences for guests, owners, property managers and agents. Horatio will be integrated as the assistant layer after the core guest and partner journeys are connected.

## Local setup

1. Install Node.js 22.13 or newer.
2. Copy `.env.example` to `.env` and provide an isolated **staging** Supabase project URL, publishable key and matching HAMLET preview API origin. Do not point development or preview builds at production.
3. Run `npm install`.
4. Run `npx expo-doctor` to validate SDK-managed dependencies; avoid automatic dependency rewrites without reviewing the Expo SDK compatibility matrix.
5. Run `npx tsc --noEmit`.
6. Run `npx expo start` for the Metro development server.
7. For native module and release-candidate QA, create an EAS development build with `npx eas-cli build --profile development --platform android` or `--platform ios`. Use an Expo Go client only when it matches SDK 58; prefer development builds for ongoing product work.

## Native authentication callback setup

The app uses the custom URL scheme `hamlet://auth/callback` for email confirmation and password recovery. Add that exact URL to the Supabase project's Authentication URL Configuration > Redirect URLs before testing email confirmation on a device. Also add the Expo development callback URL generated by `npx expo start` when testing in Expo Go or a development client. Do not add broad wildcard production redirects.

Google and Apple native OAuth are not yet wired. The existing web OAuth callback must not be assumed to work with the native scheme.

## Backend integration rules

- Reuse the existing HAMLET Supabase project, schema, RLS policies and server-side API routes.
- Do not create a second database or duplicate the web application's data model.
- Never trust client-submitted prices, fees, booking states or payment status.
- Use the existing central pricing and quote contract on the server.
- A booking request is not a confirmed booking.
- Only verified payment-provider webhooks may confirm payment.
- Keep refundable caution deposits separate from accommodation revenue and partner allocations.
- Respect owner-authorised property access and server-enforced role permissions.
- Never expose private guest identity records to owners or agents by default.
- Only `EXPO_PUBLIC_` values belong in the mobile bundle. Never add service-role or payment-provider secret keys.

## Current implementation status

Implemented in this branch:
- Expo project configuration, navigation shell and HAMLET visual foundation.
- Guest discovery and approved property catalogue.
- Sanitised public API endpoints for approved stays and property detail.
- Native email/password sign-in, guest registration with name/phone metadata and password reset request.
- Native auth deep-link callback, email confirmation and password update flow.
- Supabase session persistence using AsyncStorage.
- Property detail view, native Android/iOS date picker, guest count and special requests.
- Guest booking request submission through the existing server-authoritative `/api/booking-requests` endpoint.
- Guest booking history and cancellation through the existing `transition_booking` RPC.
- Guest profile editing for full name and phone using Supabase Auth user metadata.
- Partner onboarding for owners, authorised managers, multi-property operators and closing agents.
- Partner application status view and native property submission/draft flow through the existing authenticated `/api/partner/properties` endpoint.

Booking requests remain requests: the property partner must confirm availability before payment opens. The native Bookings screen now hands eligible `awaiting_payment` bookings to the existing authenticated `paystack-initialize` Edge Function. The app opens only the returned Paystack HTTPS checkout URL and refreshes booking state when returning to the foreground; only the signed webhook confirms payment.

Still to implement and test: richer agent lead pipeline and commission dispute workflow, caution-deposit inspection/refund flow, push notifications, Horatio, Google/Apple sign-in, app icon/splash screen, accessibility and end-to-end physical-device QA.

The current production marketplace geography is Lagos-only; Abuja and Ibadan are shown as coming later until the backend geography guard is expanded.

## Environment isolation

EAS development, preview and production profiles map to the corresponding EAS environments. Configure each environment separately:
- `development` and `preview`: dedicated staging Supabase project, staging publishable key, and the matching HAMLET preview API deployment.
- `production`: production Supabase project and approved production API origin, only after release approval.

The app no longer silently falls back to `www.hamlet.rest` when the API origin is missing. Missing configuration fails closed. Never run test bookings or payment tests against production. Keep Paystack secrets server-side in the matching Supabase project.


## Secure guest payment handoff

The native Bookings screen now invokes the existing authenticated Supabase Edge Function `paystack-initialize` only for bookings in `awaiting_payment`. The function derives the charge amount from the trusted booking record and returns the Paystack checkout URL. The app validates the returned HTTPS checkout host before opening it. Payment is not treated as complete on app return; the existing signed Paystack webhook remains the only confirmation authority. If Paystack is not configured, checkout returns a controlled unavailable response and the guest is not directed to an external/manual payment route.
