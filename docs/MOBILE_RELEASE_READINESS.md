# HAMLET Mobile Release Readiness

This checklist is the release gate for the Expo Android/iOS application. It is intentionally separate from the web marketplace release. Completing code-level CI does not mean the app has been verified on physical devices or is ready for store submission.

## Current release posture

- Mobile implementation is on `feat/hamlet-expo-mobile-app` and is proposed through draft PR #94.
- Latest application/workflow validation commit: `5753647892c80acaff670f57fec6ebac93c8482f`; the current branch may contain later documentation-only commits.
- All three required code-level workflows passed on that exact validation commit:
  - HAMLET Mobile Checks run #43981710704: clean `npm ci`, Expo Doctor and TypeScript.
  - HAMLET CI run #43981710609: lint, unit/PGlite database tests, production build and mobile/desktop Playwright tests.
  - Referral Release Validation run #43981710630: isolated Supabase migrations/database tests, lint, regression tests, production build and browser journeys.
- `apps/mobile/package-lock.json` is committed (npm lockfile v3, generated from the actual mobile manifest using Node 22). The mobile workflow uses `npm ci --no-audit --no-fund`.
- The validation runs are code/CI evidence only; they do not constitute physical-device, staging provider, or store acceptance.
- Supabase Preview did not run because no Supabase Branch is associated with the PR.
- No production database migration, production deployment, or production booking/payment test is authorised by this checklist.
- Physical Android and iOS device testing remains outstanding.

Re-check the branch HEAD and its CI checks before relying on the validation statement above. A later commit requires fresh checks.

## 1. Staging environment

- [ ] Create or identify a dedicated staging Supabase project. Do not use production for development or preview builds.
- [ ] Apply the reviewed mobile-required migrations to staging only.
- [ ] Configure EAS `development` and `preview` environments with:
  - `EXPO_PUBLIC_SUPABASE_URL`: staging project URL.
  - `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: staging publishable/anon key.
  - `EXPO_PUBLIC_HAMLET_API_URL`: matching staging/preview API origin.
- [ ] Confirm the API deployment uses the same staging Supabase project and schema.
- [ ] Configure the exact native redirect `hamlet://auth/callback` in Supabase Authentication URL Configuration.
- [ ] Add the exact Expo development callback URL generated by the local development session; do not use broad wildcard redirects.
- [ ] Confirm the `property-media` bucket can serve uploaded public listing images and that authenticated insert/delete policies restrict writes to the user's own folder.
- [ ] Configure Paystack only in the staging server/Edge Function environment. Keep secret keys out of EAS client variables and the app bundle.
- [ ] Confirm Resend/email delivery is configured in staging if email confirmation and password recovery are being tested.

## 2. Reproducible build and app identity

- [ ] Replace any floating `latest` dependency ranges with Expo-SDK-58-compatible pinned versions after checking the SDK compatibility matrix.
- [ ] Generate and commit `apps/mobile/package-lock.json` using npm from the actual mobile manifest; do not handcraft the lockfile.
- [ ] Update the mobile CI install step to use `npm ci` once the lockfile is committed, then verify Expo Doctor and TypeScript on that exact commit.
- [ ] Confirm the proposed identifiers `com.abundanceabodes.hamlet` are available and owned by the intended Apple and Google developer accounts before creating store records.
- [ ] Add approved app icon, Android adaptive foreground icon, splash artwork and store screenshots.
- [ ] Confirm display name, version/build numbering, privacy policy URL, support contact and store metadata.
- [ ] Confirm EAS project ownership and configure the production EAS environment only after release approval.

## 3. Physical-device acceptance tests

Run on at least one supported physical Android device and one supported physical iPhone. Record device model, OS version, app build number, tester, date and pass/fail evidence.

### Account and session
- [ ] Register a new guest account and verify email confirmation.
- [ ] Sign in, sign out, relaunch and confirm session persistence.
- [ ] Request password reset, open the exact deep link and complete password update.
- [ ] Confirm expired sessions and missing environment configuration fail safely.
- [ ] Verify role-aware navigation for guest, approved owner/manager, closing agent and pending applicant accounts.

### Guest journey
- [ ] Load only approved public Lagos properties.
- [ ] Open a property and confirm image, capacity, dates and amenities render correctly.
- [ ] Test unavailable dates, invalid date ranges and guest capacity limits.
- [ ] Confirm quote totals are server-generated and itemised; client values never determine the payable amount.
- [ ] Submit a booking request and verify it remains a request until partner action.
- [ ] Refresh booking history and test cancellation only where the server permits it.
- [ ] For an accepted booking in `awaiting_payment`, initialise staging Paystack checkout.
- [ ] Return from checkout without paying and confirm the app does not mark the booking paid.
- [ ] Complete a staging payment and confirm only the verified webhook changes payment status.

### Partner journey
- [ ] Join the partner network for each supported role.
- [ ] Verify network membership alone does not grant property-management permissions.
- [ ] Submit an authority application and test pending, approved, needs-correction and rejected states.
- [ ] Create a private draft and submit a property for review.
- [ ] Select multiple photos, deny and grant photo permission, cancel selection, remove photos and retry after picker errors.
- [ ] Verify image resize/re-encoding, 12-photo limit, 5 MB optimised upload limit and own-folder Storage policy.
- [ ] Force an intake API failure and verify uploaded-object cleanup where policy permits.
- [ ] Confirm unapproved listings never appear in public discovery.
- [ ] Test partner booking review, availability controls, pause/resume and referral links against staging data only.
- [ ] Confirm one partner cannot access another partner's properties, guest records or bookings.

### Quality and accessibility
- [ ] Test small-screen layouts, keyboard overlap, safe areas, scrolling and orientation behavior.
- [ ] Check labels, accessible names, focus order, text scaling, contrast and screen-reader announcements.
- [ ] Test slow network, offline state, API errors, expired auth and repeated taps.
- [ ] Confirm loading, empty, success and failure states are clear and do not leave controls stuck.
- [ ] Confirm no secrets, access tokens, private guest details or payment credentials appear in logs or screenshots.

## 4. Release decision

A release candidate can be considered only when all of the following are true:

1. Current branch HEAD has passing required CI checks.
2. Staging migrations and API configuration have been independently verified.
3. Android and iOS physical-device acceptance tests are complete with evidence.
4. Security/RLS and payment webhook checks pass in staging.
5. App identity, artwork, privacy/support information and store accounts are confirmed.
6. Product owner explicitly approves the release and production cutover.

Until then, keep PR #94 as a draft. Do not merge, submit to stores, change production domains, apply migrations to production, or run production test bookings/payments as part of this checklist.
